directory variant A

Grouped by the moment you reach for them. Four panels answering “where am I right now?” rather than “whose job is this?”. Each panel opens with one skill to type; the rest of the panel is what that first skill can hand off to.

Twenty-one skills. You only ever type one.

Every skill is a real command. Type the one that matches where you are, and it routes you to the rest — you never have to hold this list in your head.

01

When you're starting out

Get the tools in place, then ask for anything in plain words.

Start with /dx-harness:dx-design
▸ dx-design
The orchestrator. Asks what you want, answers rule questions, routes you to the right skill.
dx-design-setup
Installs the per-user tools the loop relies on, then shows you around.
dx-design-git
Gitty — explains git in plain words and does it with you safely.
dx-design-feedback
Files an issue against the harness the moment something confuses you.
02

When you're making something new

Decide what you're building, agree the plan, then build it once.

Start with /dx-harness:dx-design-execute
▸ dx-design-execute
The only skill that builds. Intent, options, a plan you approve, then the change.
dx-design-language
Defines your design language and writes DESIGN.md, so the rules stop living in your head.
dx-design-research-brief
A research plan that settles what you're asking before you recruit anyone.
03

When the page already exists

Grade it whole, or take one dimension at a time. All of these propose; none of them edit.

Start with /dx-harness:dx-design-critique
▸ dx-design-critique
Grades the whole page and ranks what to improve, with a shareable evidence report.
dx-design-pattern
Structure, hierarchy, density, and whether the page is using the right named pattern.
dx-design-polish
Spacing, type, radius, colour — one named dimension at a time.
dx-design-motion
Transitions and easing, with reduced-motion variants built in.
dx-design-flow
Multi-step tasks: traversal, async states, escape routes, draft safety.
dx-design-copy
Voice, tone, and error-message anatomy, applied as the text is written.
04

When you're shipping the code

Eight skills that carry a change from an idea to a merged pull request. These come along for the ride — the design skills are the point.

Start with /dx-harness:dx-create-issue
▸ dx-create-issue
Issues structured for an agent to implement.
dx-groom-issue
Fills in the technical sections of an issue someone else wrote.
dx-split-issue
Breaks an issue into children, each one a single pull request.
dx-implement-issue
Implements a groomed issue end to end.
dx-code-review
Seven-angle review, with findings posted inline on the pull request.
dx-lint-setup
Detects your stack and configures linting and formatting.
dx-git-hooks-setup
Pre-commit and pre-push gates around the checks you already run.
dx-update-npm-dependencies
Audits and bumps vulnerable packages, with a release cooldown.

We build ours. We curate the rest.

Three skills we didn't write and don't maintain, but reach for often. Install them alongside the harness — they carry no dx-harness: prefix and no catalog behind them.

  • /web-animation-design Easing, timing, and springs, argued from first principles.
  • /better-ui A second opinion on a component you've already built.
  • /make-interfaces-feel-better The small craft details — optical alignment, borders, hover feel.
  • Externals sit here, after the panels, so the last thing you read is generous rather than promotional. They could also sit as a fifth panel in the grid (reads as ours — risky), in the footer (safe, easily missed), or on a dedicated /skills page with the full directory (best once the list grows past 21).
  • Panel 04 deliberately spans the full row: two columns of eight short rows, so the engineering set reads as a block rather than as a third of the attention.
  • Unresolved: panels 01 and 02 are much shorter than 03, so the equal-height row leaves dead space. Either let the panels find their own height in a masonry-ish column layout, or move a skill or two to even them up.
