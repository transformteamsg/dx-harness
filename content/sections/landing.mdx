Your agent already builds the UI. The harness gives it one front door, checkable
standards, and an independent reviewer before the work ships.

Route → build → check → review → ship.

## Core features of the design harness

The four parts everything else hangs off.

**One way in. One way to ship.** Ask in plain words. `dx-design` routes you to the
right pass, and only `dx-design-execute` edits your product.

**Not every rule is a lint check.** Every control carries a tier, so you know which
rules never bend and which leave room for judgement.

**Your design language, written down once.** Keep product decisions and standing
overrides in one file the whole team, human and agent, can work from.

**The builder never grades its own work.** A fresh-context reviewer reads the
contract, screenshots, and controls, then sends findings back through the same gate
for a re-check.

## How it works

The whole harness on one map. You brief one skill; everything else works behind it.

1. **You**, in the chat — one ask, in plain words. You never pick a skill.
2. **`dx-design`, the single front door**, in the harness plugin — the orchestrator
   grills first, then routes. Rule and waiver questions stop here too.
3. **The propose-only passes**, dispatched as subagents — copy, flow, pattern,
   motion, and polish plan for `dx-design-execute`, the one builder.
4. **Shared context**, in the harness plugin — every skill reads the same control
   catalog, tokens, and components.
5. **`DESIGN.md`**, in your product repo — your product decisions and deviations stay
   where any agent can read them.

## Skills collection

Grouped by the job each skill does in the flow. Everything is one command away.

| Group | What it is for | Start with |
| --- | --- | --- |
| Getting started | None of these change your product; they get you set up and unstuck. | `/dx-harness:dx-design` |
| The design loop | Critique finds the work and numbers it; execute is the only skill that changes your product. | `/dx-harness:dx-design-execute` |
| The five passes | The loop routes to these, one named dimension each; you rarely type them yourself. | `/dx-harness:dx-design-pattern` |
| Shaping the work | Settle an open question and write it down, so the loop has something to hold you to. | `/dx-harness:dx-design-research-brief` |
| Shipping the code | Carry a change from an idea to a merged pull request. | `/dx-harness:dx-create-issue` |
| Repo upkeep | Set the gates once and they catch things before a reviewer has to. | `/dx-harness:dx-lint-setup` |
