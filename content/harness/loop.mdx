`dx-design` keeps a design run coherent from the first request to the reviewed
result. It clarifies the intent once, then carries the same context through every
specialist, subagent, builder, and reviewer. No stage starts the interview again or
silently changes the brief.

## What grounds the run

Two sources guide every decision. The [control catalog](/standards/catalog) is the
portfolio rulebook: the orchestrator filters it to the controls that apply to this
product, audience, surface, and phase. [`DESIGN.md`](/harness/skills#the-design-language)
holds the decisions that make this product itself, including its essence, colour,
type, motion, voice, guardrails, and standing overrides.

The two files do different jobs. `DESIGN.md` adds product context; it never copies
or replaces catalog rules. Existing code remains the authority for implemented
components and tokens.

## How `dx-design` orchestrates the work

For a broad improvement, `dx-design` captures the surface and brings in only the
specialists the request needs. Copy, pattern, polish, motion, and flow can run as
propose-only subagents. Each receives the same intent, `DESIGN.md` context, and
in-scope controls, then returns focused, ranked findings to the orchestrator. None
of them edits the product.

The orchestrator combines those findings into one plan, asks for approval once,
and hands the accepted work to `dx-design-execute`. A specialist can also run on
its own when you already know which dimension needs attention; it still proposes
changes rather than making them.

## How design review closes the loop

Whoever started the run launches `dx-design-review` after implementation. This is a
separate, fresh-context agent. It receives the original intent, approved plan,
screenshots, component inventory, relevant catalog controls, and any standing
overrides from `DESIGN.md`.

The reviewer reports findings but never edits the product. The builder addresses
them, then the same reviewer checks new screenshots and marks each finding resolved,
partial, or unresolved. The builder's explanation is not evidence.

## Where you decide

The run stops once before implementation for plan approval. You see the proposed
structure, content, states, controls, and any requested waivers before code changes.
An explicit request to build a specific plan or chosen direction already counts as
approval.

Agents can report a deviation but cannot approve one. You decide whether to grant a
permitted waiver at plan approval. After design review, the person who approved the
plan also decides whether an unresolved finding may remain open.
