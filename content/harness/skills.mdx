A skill is a command you type in Claude Code. The plugin ships 21 skills:
13 for design work and 8 for engineering workflow. The design family carries
the `dx-design-` prefix. They install together when you
[install the plugin](/harness/install). You do not need to memorise the list:
type `/dx-harness:dx-design` and it works out what you need and routes you.

Two rules hold for every skill:

- **You cannot break anything by asking.** One skill edits the product:
  `dx-design-execute`. It stops and shows you a plan before it writes code.
  Every other skill proposes; it does not edit.
- **You can answer in plain words.** "The page feels cluttered" is a valid
  instruction. The skill translates it into the standard's terms.

| --- | --- |

## The front door

**`/dx-harness:dx-design`** is the orchestrator. It asks what you want, one
question at a time. If you cannot say, it offers five plain modes: make
something new, improve what exists, brainstorm, define your design language,
set up or fix your tools. It routes you and hands your answers over, so no
skill interviews you twice.

It also answers rule and waiver questions — "does TOK-1 apply here?", "can I
waive this, and who approves?" — with citations from the catalog, then offers
the one next step that fits. It never builds.

## The builder

**`/dx-harness:dx-design-execute`** is the only skill that edits the product.
It runs the loop: intent → diverge → plan approval → implement → design
review → rule proposal. You describe the screen in your own words; it comes
back with 2–3 genuinely different directions as real HTML pages; you pick
one. No code exists until you approve the plan. If you change your mind
mid-run, say so — the loop goes back a phase rather than pushing on.

It also builds the findings you accept from the critique and specialist skills.

## Specialist skills and subagents

`dx-design` brings in focused specialists when a request needs more than one
kind of design judgement. It gives each specialist the same intent, relevant
`DESIGN.md` decisions, and in-scope control catalog entries. They return their
findings to the orchestrator, so you get one coordinated plan rather than a
set of disconnected recommendations.

The five specialists below can run in two ways. Call one directly when you
already know which dimension needs attention. For a broader improvement,
`dx-design` runs the relevant ones as propose-only subagents. Each can record
up to five ranked findings on the surface's design ticket, but none edits the
product.

- `/dx-harness:dx-design-copy` — wording, tone, names, error messages.
- `/dx-harness:dx-design-polish` — spacing, type, colour, radius, shadow.
- `/dx-harness:dx-design-motion` — transitions, easing, timing, reduced motion.
- `/dx-harness:dx-design-flow` — multi-step tasks: steps, waiting states, safe exits, drafts.
- `/dx-harness:dx-design-pattern` — structure, hierarchy, density, and whether
  the page uses the right named pattern (list vs cards, master-detail,
  wizard). It can propose a whole-page rebuild that keeps the same content.

**`/dx-harness:dx-design-critique`** is the whole-page specialist for "I do
not like this page but I cannot say why." It captures the page, grades it
against the catalog, and returns ranked findings with scores. It also handles
re-audits. Like the five specialists, it proposes changes but never builds
them.

The orchestrator merges accepted findings into one ranked plan and asks for
approval once. `dx-design-execute` then builds that plan. After implementation,
`dx-design` sends the full result to the separate `dx-design-review` agent, which
checks the original intent, approved plan, `DESIGN.md`, and relevant catalog
controls. The same reviewer re-checks fixes from new screenshots.

## The design language

**`/dx-harness:dx-design-language`** defines your product's design language
and writes `DESIGN.md` — the per-product decisions any agent can read. It
scans your code first: on a healthy repo it mines the answers and asks you to
confirm or correct; on a token-less repo it interviews you. It can ingest
Figma and brand documents. It never writes product code.

## Behind the scenes

- `/dx-harness:dx-design-git` is Gitty, a friendly git companion for
  designers who design in code. It also runs the branch guard: when a build
  starts on `main` or behind the remote, it proposes the fix before anything
  changes.
- `/dx-harness:dx-design-feedback` files a GitHub issue on the harness repo
  the moment something about the harness itself confuses you, even mid-task.
  Confusion is a bug report, not a you-problem.
- `/dx-harness:dx-design-research-brief` writes a research plan that aligns a
  study before a participant is recruited.
- The **design reviewer** (`dx-design-review`) is an agent, not a command:
  after `dx-design-execute` builds something, a separate agent grades the result
  against what you asked for, then re-checks each fix. The builder never
  marks its own homework.

One deliberate stance carried by every skill: **unwarranted novelty is
flagged as readily as generic output.** A custom pattern where a stack
component already exists is a finding.
