Install the harness skills

The harness ships as a Claude Code plugin. In your product repo — Teacher Workspace, CaseSync, or Glow — add the marketplace and install it. Two commands, typed in Claude Code:

/plugin marketplace add transformteamsg/tfx-design-standard
/plugin install tfx@tfx
/reload-plugins

That installs the eleven skills, the evaluator that grades the work, and the control catalog — the rulebook ships with the plugin, not your repo. You're set.

Working on the harness itself? No install needed — open a Claude Code session in the harness repo and the skills load from .claude/skills/ automatically.

Already have it?

Only if you're on the old tfx-design-harness plugin (from before the 0.3.0 rename) do you reinstall — the old and new are separate plugins, so an update won't cross the rename:

/plugin uninstall tfx-design-harness
/plugin marketplace update tfx
/plugin install tfx@tfx
/reload-plugins

Your product's DESIGN.md and decision records are untouched. Full detail: docs/UPDATING.md.

What it is

A control catalog plus a set of Claude Code skills. Together they make an agent follow the TFX Design Standard whenever it designs or changes UI for the Teacher & School portfolio — Teacher Workspace, CaseSync, and Glow.

The point is to keep quality from drifting. Instead of hoping an agent remembers the rules, the harness loads them, applies them, and grades the result against what you asked for. Its brand essence is Kind Utility: useful first, kind at the surface. The one test any screen has to pass — does this help teachers work faster with less stress?

How it works

A six-phase loop, and one phase is yours

The agent runs all six phases. You only step in at Phase 3 — approving the plan, the cheapest place to catch a wrong turn.

1IntentPin down the brief — what the page is for, who it's for, when it's done.
2DivergeA few rough directions, no pixels yet. You pick one.
3Plan· your gateApprove or adjust before anything's built. A wrong turn caught here is a chat, not a rebuild.
4ImplementThe agent builds exactly what you approved — your tokens and components, no AI slop.
5VerifyA separate agent checks it against the brief. Anything off-brief is a bug.
6RatchetLessons from the run become new rules — the bar only goes up.

The rulebook is tiered

Nobody memorises it — the agent loads and applies the catalog. Each control carries a tier that decides how hard it binds.

L0Never bends. Accessibility floor and destructive-action safety. If one seems impossible, that's a question for you, not a judgment call.
L1Must pass, or a named human waives it on the record.
L2Strong default. Deviate only with a specific, real reason.

The skills are grouped by what you're doing

You don't pick a tool by its name. You say what you want, and the right skill answers.

Get started in three steps

1

Orient — /tfx:start

A few lines on how the harness works, a check that your machine is ready, and a hand-off to the right skill.

2

Set up — /tfx:setup

Installs what the loop needs: screenshot capture, issue filing, the check scripts. It can also seed a product's DESIGN.md so the loop knows that product's colours, tone, and grid.

3

Say what you want

No need to name a skill. The router below shows where common asks land.

"Build a page or flow"design
"Review or improve this page" (no specific change named)critique
"Fix the wording"copy
"Polish the spacing or type"polish
"The animation feels off"motion
"This multi-step flow loses my work"flow
"Tighten the structure or hierarchy"layout
"Can I waive this rule? Who approves?"standards

How to give feedback

When the harness itself gets in your way, say so — even mid-task. The feedback skill captures it and files a [harness-feedback] issue on the repo for you.

Use it for: "The plan gate keeps interrupting me for tiny copy changes." · "The contrast check flagged a disabled button." · "The token check missed a raw hex I snuck in."

Not for: feedback about a product's own page (that's a design-loop task), or proposing a new rule (that's the ratchet, below).

How to contribute

The catalog grows one way: from evidence, never speculation. A defect no control caught, a waiver you keep granting, or an update to the standard — each can become a new rule. This is the ratchet.

1

Propose

Write a draft record in docs/catalog-changes/: the rule, the evidence behind it, and the re-audit set — which existing surfaces it would affect.

2

Open a lightweight PR

You propose; the design lead approves. Nothing enters the catalog without a named human's sign-off.

3

It lands, and everything downstream re-audits

The new rule ships, and surfaces it touches get re-checked. Evals follow the same discipline — every escaped defect becomes a test.

Two rules that never bend: never edit the catalog to make a failing check pass, and L0 is never waived. Everything else is a conversation.
